# D-1: `cycle` is a parametric radial template, not a layered graph layout

A blocking divergence between the requirements and the plan, found by looking at
`docs/reference/rendered/cycle-review-layered-down.svg`.

## What the spec requires

`docs/theme-requirements.md` §6 lists **Cycles** under "Specific shapes",
alongside concentric circles and pyramids:

> **Cycles.** If it is a cycle, it should look like one: steps spaced evenly,
> arrows all following the same direction, no crossings.
>
> **Implication.** These are parametric templates, not graph layout.

## What the plan says

`status/plan.md` T11 groups `cycle` with `flow` and `tree` as graph kinds, with
deps `T4, T10` — behind the layout engine and orthogonal routing.

## What that produces

The `cycle-review` reference document, five nodes in a ring, laid out by the
layered engine:

```
5 boxes, all at x=24.0, stacked at y = 24.0, 84.8, 145.7, 206.6, 267.4
5 edges, ALL on the vertical line x=126.1
```

A column of boxes with one line drawn down through it. The back edge retraces
the four forward edges exactly, so the "cycle" is invisible. It does not read as
a cycle, and no amount of routing work in T9 will make it one — a layered cycle
routed orthogonally is still a column with a line around the side.

## The fix

Render `cycle` the way `pyramid` and `rings` are rendered: parametric geometry,
no layout engine.

- `n` nodes evenly spaced on a circle, first at the top, going clockwise.
- The radius follows from the node box sizes and the theme's spacing, and the
  whole figure is fitted to the canvas width.
- Edges are arcs (or short chords) along the circumference between adjacent
  nodes, all following the same direction, so no edge crosses another and every
  arrow reads as continuing the loop.

**This changes the dependency graph.** As a parametric template `cycle` does not
need T9 or T10 — its edge geometry is its own — so it depends on T1, T4 and T6
only, exactly like T13. It is unblocked now. T11 then covers `flow` and `tree`.

## Acceptance gate

`text_overflow_count == 0`, plus the plan's own cycle test, which is currently
filed under T11:

`test_cycle_arrows_all_follow_one_direction` — a cycle reads as a cycle.

Add:
`test_cycle_steps_are_evenly_spaced_around_the_circle` — the angle between
consecutive nodes is constant.
`test_cycle_no_edge_crosses_another`.
`test_cycle_of_two_nodes_still_reads_as_a_loop` — the degenerate case.

```bash
uv run pytest tests/test_kinds_cycle.py -q
uv run ruff check .
uv run mypy .
```

## Location

`src/drawspec/kinds/cycle.py` (new), `tests/test_kinds_cycle.py`.
Register it in `kinds/__init__.scene_for` and `IMPLEMENTED`.

## Note on the T7 decision

`cycle-review.json` was one of the three documents in T7's engine comparison.
That comparison is still valid as a test of **cycle breaking**, which is a real
engine capability, but the render is not how a `cycle` document will be drawn.
T7's decision does not rest on it: the deciding measurement was `flow-validation`
at 539 (fits the 640 canvas) against grandalf's 672 (does not).
